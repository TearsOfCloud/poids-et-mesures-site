# Carrousel 4:5, 8 slides (analyse, pas une copie du Reel)

1. **Titre : Arrête de tout réexpliquer.** Corps : GitHub publie un guide sur les « skills » : des notices que l'on écrit une fois et que l'IA relit à chaque fois.
2. **Titre : Une skill, c'est quoi ?** Corps : Un dossier centré sur un fichier SKILL.md. Il dit quand utiliser la skill et comment faire la tâche. Source : GitHub, 12 novembre 2026.
3. **Titre : À quoi ça ressemble.** Corps : Le fichier commence par un nom et une description. Exemple de GitHub : name : proof-agent. Description : vérifier le travail d'une IA avec un vérificateur indépendant.
4. **Titre : Pourquoi un second regard ?** Corps : Si la même IA juge son travail, son explication peut influencer la relecture. GitHub résume : s'auto-vérifier n'est pas vérifier. Le vérificateur doit citer des preuves.
5. **Titre : Une notice, pas une clé.** Corps : Une skill peut expliquer comment interroger une base de données. Elle ne donne pas l'accès. Outils, identifiants et droits viennent de l'outil qui l'exécute.
6. **Titre : Garde les noms à part.** Corps : GitHub range les noms de projet dans un seul fichier de configuration que toutes les skills lisent. Ainsi, une autre équipe réutilise les skills sans les réécrire.
7. **Titre : Quand ça vaut le coup.** Corps : Tâche bornée et répétée : liste de contrôle, publication, migration. Si tu as besoin d'un journal d'audit ou de droits imposés hors de l'IA, une vraie application convient mieux.
8. **Titre : Ton essai du jour.** Corps : Choisis la tâche que tu réexpliques le plus. Écris : ce qu'il faut, où ça s'arrête, ce que tu vérifies. Teste avec un autre assistant. Chiffres : aucun, c'est un guide de GitHub, pas une mesure.
